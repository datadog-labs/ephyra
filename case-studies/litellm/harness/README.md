# litellm harness (ephyra)

`build.sh <src> <build> [coverage]` creates `<build>/venv` (uv, locked deps, the project is not installed)
and builds the Rust driver `<build>/search`. It also copies `worker.py` and writes `<build>/env.sh`, which sets
`PYTHONPATH=<src>` so litellm is imported from the tree. In coverage mode it writes
`coverage.json` (`coveragepy`), and the worker runs under `coverage run -p --source=<src>/litellm` whenever
`COVERAGE_FILE` is set.

`run.sh <build> <seed> <secs> <out>` starts one driver process. The driver owns one long-lived Python worker
(`worker.py`) and talks to it over a JSON-line protocol. The worker runs a local mock HTTP server with
TCP_NODELAY. The driver repeatedly runs `ephyra::check` (200 tests, 30 s or less per call) and alternates
between providers.

## Case (generated by ephyra, `driver/src/main.rs`)

A case is one logical provider response with these parts:

- **Content blocks:** text, thinking with a signature, redacted thinking, and tool_use. Tool arguments are a
  JSON object with keys from a small pool and values that are strings, ints, big ints, floats, lists or objects.
- **Fragmentation:** text, thinking and tool arguments are split into fragments, and a fragment can be empty.
  The alphabet includes multi-byte UTF-8, JSON specials and U+2028.
- **Response metadata:** the stop reason, the model (3 models per provider, all in the cost map), and usage
  (input, output, cache read, cache creation, reasoning). Usage values include tier edges such as 200k.
- **Delivery:** TCP write sizes, cycled, so splits fall inside UTF-8 characters and JSON. Other options are
  ASCII or raw UTF-8 JSON, Anthropic `message_delta` usage given as output-only or full, and the sync or
  async stream API.

Providers:

- `anthropic`: Messages API JSON and SSE.
- `openai`: chat.completion, and chunk SSE with a usage chunk.
- `gemini`: Google AI Studio `generateContent` and `streamGenerateContent?alt=sse` (CRLF framing). Thought
  parts carry an optional `thoughtSignature`, and function calls are streamed whole. `usageMetadata` goes on
  the last chunk, or on every chunk when `delta_usage_full` is set.

- `bedrock`: Amazon Bedrock Converse (`bedrock/<model id>`, dummy AWS credentials, `api_base` = the mock):
  `/model/{id}/converse` JSON and `/converse-stream` as a binary AWS event stream (`aws_frame`: prelude,
  string headers `:event-type`/`:content-type`/`:message-type`, CRC32s), with `reasoningContent` text +
  signature deltas, base64 `redactedContent`, `toolUse` start/input deltas, `messageStop` and a `metadata`
  usage event (`cacheReadInputTokens`, `cacheWriteInputTokens` and a 5m/1h `cacheDetails` split). Models:
  Claude Sonnet 4.5 / Opus 4.6 (cross-region ids) and Nova Pro. Through `litellm.anthropic.messages` the
  Claude models go to `/invoke` and `/invoke-with-response-stream` (Anthropic Messages bodies, each SSE
  event in a `chunk` frame's base64 `bytes`), which the mock serves as well. On Bedrock cases a
  `response_format` is generated (none / `json_object` / `json_schema`): when litellm injects the forced
  `json_tool_call` tool, the mock answers with one such toolUse (thinking first, no text) and the content
  must be that tool input (compared as parsed JSON); `req__response_format__bedrock_chat` checks the schema
  reaches Bedrock (as `outputConfig.textFormat` or as the json_tool_call input schema).

## Oracles

1. `stream`: litellm parses the same payload twice, once as `completion()` and once as
   `stream_chunk_builder(list(completion(stream=True, stream_options={"include_usage": True})))`. The two
   results must agree on content, reasoning_content, thinking_blocks, tool_calls (id, name and args parsed as
   JSON), finish_reason, usage (prompt, completion, total, cached, reasoning, cache_creation, cache_read) and
   `completion_cost`. Signatures look like `stream__<field>__<provider>`.
2. `model`: on both paths, the content must equal the concatenated text blocks and the tool calls must equal
   the generated ones (`model__content|tool_calls__<provider>_<path>`).
3. `crash`: any exception on the non-stream call, the stream, the builder or `completion_cost` on a
   well-formed provider response. Signatures look like `crash__exception__<provider>_<path>`. A worker that
   dies gives `crash__worker_died__<provider>`.
4. `hang`: no answer within 60 s (`hang__timeout__<provider>`).
5. `cost`: a cost that is negative, NaN or infinite (`cost__invalid__...`).

Each oracle kind panics at its own line (`fail()` in main.rs), so shrinking keeps the failure it started
with. Once this process has reported a signature, later cases with the same signature are passed on and
counted in `stats.json` under `known_sig_skips`.

6. `resp` and `msgs` (bridges, on a quarter of the cases each, after the chat checks pass): the same payload
   through `litellm.responses()` / `aresponses()` (for anthropic and gemini the Responses-to-chat bridge in
   `litellm/responses/litellm_completion_transformation`; for openai the native `/v1/responses`, which the
   mock serves as Responses API JSON and SSE) and through `litellm.anthropic.messages.create` / `acreate`
   (native pass-through for anthropic, the chat adapter for gemini, the Responses adapter for openai).
   Each is checked against the case (`<bridge>__model_content|model_tool_calls__<provider>_<path>`), and
   stream vs non-stream: Responses text, tool calls, status, incomplete reason and usage of the final
   `response.completed` vs the non-stream response, `*.done` events vs their deltas, and increasing
   `sequence_number`; Messages text, thinking, tool_use, stop_reason, usage and thinking signatures of the
   message rebuilt from the SSE events vs the non-stream message. Signatures `resp__<field>__<provider>`,
   `msgs__<field>__<provider>`. The Messages stream is async for anthropic and openai (their handlers have
   no sync stream). In the Messages comparison text and thinking are compared joined, since the non-stream
   message comes from a chat completion that loses block order, and empty text blocks are dropped
   (`mask_msgs_empty_text_block`).

7. `req` (request translation, on 3/4 of the cases): the case also carries a generated conversation
   (`Req` in main.rs): system/developer prompts, user turns (text parts as a string or a list, JSON-looking
   text, an optional base64 PNG/JPEG data-URL image), assistant turns with text and 0-3 tool calls (id
   shapes `call_N`, `toolu_0N`, `functions.<name>:N`, `call-N`, `N`, a long `fc_...`; ids unique; arguments
   often empty so identical parallel calls happen), one tool result per call (optionally in reverse
   order; the first may carry an image), declared tools, tool_choice (auto/none/required/by name), stop, max_tokens and
   parallel_tool_calls. It is sent in each caller API's format: chat messages for `completion()`,
   Responses input items for `responses()`, Anthropic messages for `anthropic.messages`. The mock records
   the provider request, and the worker reads it back (Anthropic Messages, Gemini generateContent, OpenAI
   chat or Responses) into a flat `(role, item)` list that must match the conversation: text, images, tool
   calls (name, arguments parsed), tool results (content; Gemini `functionResponse` name and the
   documented JSON-object parsing), and the pairing of tool-call ids (ids may be rewritten, but distinct ids
   stay distinct and results point at their call; Anthropic ids must match `^[a-zA-Z0-9_-]+$`). Also checked:
   system text, tool declarations, tool_choice, stop, max_tokens, parallel_tool_calls, and that the stream
   call sends the same request as the non-stream call (minus `stream`/`stream_options`). Signatures
   `req__<field>__<provider>_<api>` (`messages_<kind of the first differing item: text|image|tool_use|tool_result|other>`, `system`, `tools`, `tool_choice`, `parallel`, `stop`,
   `max_tokens`, `tool_id`, `stream_diff`, `count`). The request checks run before the response checks.
   Normalisations (counted): text compared with whitespace removed and adjacent text parts of one role
   joined (adapters join them); within a run of assistant items text comes first (the Responses adapters
   emit function calls before the message item); blank text and Anthropic's empty-text placeholder are
   dropped; o3-mini's system prompts go as user messages on the chat path (no `supports_system_messages`);
   params a model does not support (stop, parallel_tool_calls for o3-mini/gpt-5) are not sent;
   Responses `max_output_tokens` is at least 16; for OpenAI, tool-result images may move into a user message
   after the tool results, behind litellm's boundary text (`TOOL_RESULT_IMAGE_BOUNDARY`); Messages API input never has blank text (Anthropic
   rejects it), so blank parts become ".".

8. `turn` (history round trip): the response goes back as the assistant turn of a follow-up request, as
   the docs show for multi-turn tool use, and the mock records that follow-up provider request. Chat
   (on the `bridge=none` cases): `response.choices[0].message` (as a dict without None fields, as the
   Message object, or as `model_dump()`, from the case's `turn` field), then one tool message per
   tool call (or a user "next"). Responses (on the `responses` bridge cases): `input += response.output`
   plus `function_call_output` items. Messages (on the `messages` bridge cases): the response `content`
   plus `tool_result` blocks. Each is done for the non-stream response and for the one rebuilt from the
   stream. The follow-up has to carry the text (whitespace not compared), the tool calls (name, args) with
   results pointing at distinct ids, the Anthropic/Bedrock-Claude thinking blocks with signatures and
   redacted data in order (with `thinking` / `reasoning` enabled), and Gemini `functionCall`
   thoughtSignatures on their functionCall parts (Gemini 3 may get litellm's placeholder on an unsigned
   first call). At least one of a Gemini response's other signatures has to come back, and no signature
   may be sent twice. The stream-derived and non-stream-derived follow-ups must be the same request, with
   tool ids canonicalised and text placed before tool calls. Responses only: SDK output objects
   (`ResponseFunctionToolCall`, ...) and the same items as dicts must give the same request
   (`turn__object_input__responses`, one signature for every provider). Signatures look like
   `turn__<text|tool_use|tool_result|thinking|signature|signature_lost|signature_dup|exception>__<provider>[_responses|_messages]_<side>`
   and `turn__stream_diff__<provider>[_responses]`.
   Generator additions: Gemini function calls may carry a `thoughtSignature` (Block::Tool `sig`). Signatures
   and redacted data are unique per block, with a 4-char base64 prefix, because litellm dedups replayed
   thinking by signature and Claude's redacted data is always base64.
   Masks: `mask_turn_empty_content` (""→None before replay), `mask_turn_blank_message_item`,
   `mask_turn_text_whitespace`, `mask_turn_text_tool_order`, `mask_turn_thinking_order` (only when the case has
   thinking after text or a tool call, which real responses do not), `turn_gemini_dummy_signature`.

9. `cache` (response cache, on 2/5 of the cases: Case `cache` = nonstream / stream): with
   `litellm.cache = Cache(type="local")` (in-memory, default call types: completion, responses,
   anthropic_messages), the case's call on its API (chat for `bridge=none`, else `responses()` /
   `anthropic.messages`) is made once (it must reach the provider and leave an entry in the cache), then
   twice more, the same way and with sync/async swapped. Both must be served without a provider request
   (`cache__miss__<path>`) and return what the first call returned: the same view as the other
   oracles use (chat: content, reasoning, thinking blocks, tool calls with their ids, finish, usage,
   thought signatures; Responses: text, tool calls, status, incomplete reason, usage of the final
   response; Messages: blocks, stop, usage), so `cache__<field>__<path>_<stream|nonstream>`. `<path>` names the code path, not the provider (which is in the message): `chat`, `responses` (openai/, native: ResponsesAPIResponse entries), `responses_bridge` (the chat-completion bridge), `messages` (anthropic/ and bedrock/ Claude, native), `messages_adapter` (gemini/, openai/). A stream hit is a
   replay of the stored assembled response (`convert_to_streaming_response[_async]`, the Responses /
   Messages cached iterators). `stream` is part of the cache key (`Cache.get_cache_key` keys every LLM API
   param), so a hit is only expected in the first call's mode. Chat hits must carry
   `_hidden_params["cache_hit"]` (`cache__flag__`) and a zero `response_cost` (`cache__cost__`, #46471
   "report zero response_cost on a response-cache hit"). Then a request with one more user message must
   reach the provider (`cache__wrong_hit__`). Crashes are `cache__exception__<path>_<store|stream|nonstream|over_limit|changed>`.
   Modelled rules: `Cache(max_messages=4)` ("Requests with more `messages` (or Responses API `input` items)
   than this are neither looked up nor stored"): such a request must not be stored and its repeat must
   reach the provider (`cache__over_limit__`, counted `cache_over_max_messages`); a first response with no
   output is not stored ("not caching a response with no output", counted `cache_skip_no_output`), nor is a
   Responses stream that ends in anything but `response.completed` (`cache_skip_responses_stream_not_completed`).
   Runs before the bridge/turn checks, whose known failures would otherwise end most of those cases.

10. `param` (optional params, on 1/3 of the cases: Case `params`): up to a dozen OpenAI chat params, each
   present with probability 1/5 — temperature (0, 0.37, 1, 1.7, 2), top_p, seed (0, 7, 123457), presence /
   frequency penalty (0 and negatives included), n, logprobs, top_logprobs, user (plain, an email, non-ASCII),
   reasoning_effort (none … xhigh), max_completion_tokens, response_format (json_object / json_schema) — and
   `drop_params` on or off, added to one more chat call with the case's conversation. Contract
   (`utils.py` `_check_valid_arg`: "`{provider}` does not support parameters: [...] To drop these, set
   litellm.drop_params=True"): a param `get_supported_openai_params(model, provider)` lists must not raise
   with drop_params on and must reach the provider request with its value (`PARAM_ALIASES` says where:
   Gemini `generationConfig.*`, Bedrock `inferenceConfig.*`, Anthropic `metadata.user_id`, ...;
   `param__<name>__<provider>_chat`, presence/frequency penalty as `penalty`); an unlisted one must raise without drop_params
   (`param__not_raised__`) and not be sent with it (`param__unsupported_sent__`); with drop_params nothing
   may raise (`param__raised__`). reasoning_effort (not "none") and json_schema response_format only have to
   be present. Then on the `responses` / `messages` bridge cases the same values in the other API's spelling
   (Responses `temperature`, `top_p`, `user`, `top_logprobs`, `max_output_tokens`, `reasoning.effort`,
   `text.format`; Messages `temperature`, `top_p`, `max_tokens`) must give the provider request what the
   completion() call gave it (`param__<name>__<provider>_<responses|messages>`; openai's Messages adapter, which goes through the
   Responses API, reports as `openai_responses`). On async cases the stream
   call must send the same params (`param__stream_diff__<provider>_chat`).
   Modelled (counted): a listed param rejected for some values before any request, with an error naming it
   (O-series "Only temperature=1 is supported", reasoning_effort levels a model lacks) and, with
   drop_params, dropped (confirmed by the same call without drop_params); Anthropic drops email user ids;
   json_object without a schema is not enforced; Responses `max_output_tokens` >= 16 (also the openai
   Messages adapter, which goes through the Responses API).

11. `error` (provider errors, on a quarter of the cases: Case `err`, run after the chat checks pass and
   before `param`): the mock answers every request of this phase with an error, and the same call goes
   through `completion()` (non-stream and stream, sync or async per the case), `responses()` and
   `anthropic.messages` (each non-stream and stream). Two shapes: an HTTP error status (400, 401, 403, 404,
   408, 422, 429, 500, 502, 503, 504, 529) with the provider's documented error body (Anthropic
   `{"type":"error","error":{"type","message"}}`, OpenAI `{"error":{"message","type","param","code"}}`,
   Google `{"error":{"code","message","status"}}`, Bedrock `{"message"}` + `x-amzn-ErrorType`), a plain-text
   body or an empty one; or (`midstream`) a 200 stream that stops after `after` events with the provider's
   error event (Anthropic `event: error`, OpenAI chat `data: {"error":…}`, OpenAI Responses `error` event,
   Google an error object, Bedrock an event-stream frame with `:message-type exception`). Contract
   (docs.litellm.ai/docs/exception_mapping): "LiteLLM maps exceptions across all providers to their OpenAI
   counterparts" with a status -> type table, and every exception carries "status_code - the http status code
   of the exception, message - the error message, llm_provider - the provider raising the exception".
   Signatures `error__<kind>__<provider>_<chat|responses|messages>[_stream]`: `not_raised` (a non-stream call
   with an HTTP error returned something), `swallowed` (a stream call with an HTTP error or an error event ended normally; a Responses/Messages
   stream that hands the error on as an `error` / `response.failed` event or passes the raw `event: error`
   through is fine, counted `err_as_event_*`), `unmapped` (not an `openai.OpenAIError`), `message` (the
   provider's message, possibly JSON- or bytes-escaped, is not in the exception), `class` (not the table's
   type; the openai SDK class is accepted too, "For OpenAI and Azure we return the original exception"),
   `status` (`status_code` differs from the HTTP status), `provider` (no `llm_provider`). Modelled: 422 may
   be BadRequestError (`mask_422_bad_request`, every provider mapping does it), 504 may be Timeout
   (exception_mapping_utils "gateway timeout error"), 500 may be APIConnectionError and 502 BadGatewayError.
   Messages are neutral (none of the words the mapping matches: context, rate, quota, ...). Per-call time is
   summed in `err_ms_<provider>_<api>[_stream]_<status>`. A case close to the 60 s hang limit dumps every
   thread's stack to the worker's stderr (`faulthandler`).

12. `router` (Router retries and fallbacks, on a fifth of the cases: Case `rt`, run after `error`): a
   `litellm.Router` with a `primary` model group (1 or 2 deployments of the case's model) and a `backup` group
   (1 deployment), `num_retries` 0-3, optionally `fallbacks=[{"primary": ["backup"]}]` and a `RetryPolicy`
   (up to 3 of its fields, 0-3 retries each), `disable_cooldowns=True`. The mock serves every deployment
   under its own path prefix (`/p0`, `/p1`, `/b0`) and answers the primary's requests from a generated
   script (up to 4 HTTP errors from the `error` statuses, or 200, in request order, then 200) and the backup's
   with 200 or one status forever. The call is the case's API through the Router (`completion` / `acompletion`,
   optionally streamed; `responses` / `aresponses`; `aanthropic_messages`). Contracts: `num_retries` "Number
   of retries for failed requests"; `litellm.should_retry` "Retries on 408, 409, 429 and 500 errors. Any client
   error in the 400-499 range [...] would not trigger a retry"; `should_retry_this_error` retries 401/403 only
   when the group has another deployment; `RetryPolicy` "If RateLimitErrorRetries = 3, then 3 retries will
   be made for RateLimitError" (the first error's class, a 404 first, then `DefaultRetries`); fallbacks: "If
   it fails after num_retries, fall back to another model group". `rt_simulate` models the request count of
   each group from the direct call's exception for each status; paths after a deployment was skipped
   (`_deployment_ids_to_skip_on_retry`) are not modelled (counted `rt_unknown_path`). Checks: request counts
   (`router__retries__`, `router__fallback__`; a single request where the model wants a retry or a fallback is
   `router__single_attempt__`), a success must return what the direct call returns
   (`router__result__`, `router__raised__`), an all-failed call must raise (`router__not_raised__`) a mapped
   exception (`router__unmapped__`) of the same class and status_code as the direct call for the last
   status (or the backup's; `router__exception__`), and chat responses carry `x-litellm-attempted-retries`
   / `x-litellm-attempted-fallbacks` (`router__retry_header__`, `router__fallback_header__`). Requests outside
   the deployments are `router__stray__`. The area is the Router entry point, not the provider (which is in
   the message): `chat`, `chat_stream`, `responses`, `messages`, `_sync` for the sync entry points.
   Back-off sleeps are off (`JITTER`, `INITIAL_RETRY_DELAY`, `MAX_RETRY_DELAY` = 0, set by the worker);
   cooldowns are off because failures are counted in logging callbacks (timing-dependent).

## Masks (all counted in `stats.json` under `masks`)

Bedrock: `req_bedrock_choice_none_unsupported` (litellm raises "Bedrock doesn't support tool_choice=none"),
`mask_bedrock_empty_required` (an added top-level `"required": []`), `skip_bedrock_resp_sequence_number`
(the bridge's sequence_number bug is already reported under anthropic/gemini),
`fix_bedrock_output_below_thinking` (outputTokens raised to at least the thinking text's byte count: litellm
estimates Converse thinking tokens from the text), `req_bedrock_parallel_no_equivalent` (Nova has no
disable_parallel_tool_use), `req_bedrock_choice_taken_by_json_tool`. In the Messages comparison redacted
thinking is compared apart from tool_use blocks (only the order within a kind is comparable).

- `mask_u2028_escaped`: raw U+2028 and U+2029 in JSON are always escaped. httpx's `iter_lines()` (a
  dependency) splits on them because it uses `str.splitlines`, which drops stream text.
- `mask_empty_content` and `mask_empty_reasoning`: `""` is treated as `None`, since both mean "no text".
- `mask_none_detail_tokens`: an absent cached, reasoning or cache_creation count is treated as 0.
- `mask_gemini_tool_id`: Gemini function calls have no id and litellm generates a random one, so tool ids
  are not compared for Gemini.
- Mock realism, not masks: Anthropic thinking signatures are never empty. The `message_start`
  output_tokens is `min(1, output)`. For OpenAI, `cached_tokens` is at most `prompt_tokens`,
  `reasoning_tokens` is at most `completion_tokens`, and an empty arguments string is sent as `"{}"`.

## Findings

Each finding is `findings/<sig>/<n>/` with `finding.json`, `case.json`, `signature`, a copy of `worker.py` and
`repro.sh`. `repro.sh <build>` runs `worker.py --repro`, which exits 1 when the same signature fails again and
0 otherwise.

## Throughput

| Build | Cases per run | Rate | Failures |
|---|---|---|---|
| Plain, 4 parallel runs of 240 s | about 6,000 | about 25 cases/s per process | 3 per run (0.05%) |
| Coverage, 2 parallel runs of 240 s | about 1,060 | about 4.5 cases/s | 3 per run |

The coverage runs reached 26% of `litellm/` lines.

Each case makes 2 litellm calls plus `stream_chunk_builder` and 2 cost calls. The ephyra report `tests`
equal `cases` minus the failing cases.
