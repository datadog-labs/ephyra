**Title:** json_valid() returns 0 for valid JSON text based on json_set call

```sql
SELECT json_set('[0x1F]', '$[1]', 2), json_valid(json_set('[0x1F]', '$[1]', 2));
SELECT json_set('[0x1F]', '$[1]', 2), json_valid('[31,2]');
SELECT json_valid('[31,2]'), json_set('[0x1F]', '$[1]', 2);
SELECT json_valid(json_set('{k:1}', '$.v', printf('%.*c', 120, 'x')));
```

Output from trunk (check-in dc388e83b05d, 2026-10-10 19:19), built from the source tarball with default options:

```
[31,2]|0
[31,2]|0
1|[31,2]
0
```

Expected `[31,2]|1` from the first two queries and `1` from the last. json_set() turns the JSON5 input into plain JSON, and in a statement of its own `SELECT json_valid('[31,2]')` gives 1, as does the last query with a standard input (`'{"k":1}'` in place of `'{k:1}'`). json1.html says that "JSON text generated by these routines always strictly conforms to the canonical JSON definition and does not contain any JSON5 or other extensions", and that json_valid() without flags returns "true only if the input X is strictly conforming RFC-8259 JSON text without any extensions". In the second query json_valid() is given a literal, and the earlier json_set() call still changes its answer: the third query, the same two calls in the other order, gives 1.

With stored values, the answer for one row can depend on an earlier row:

```sql
CREATE TABLE t(j);
INSERT INTO t VALUES ('[0x1F]'), ('[31,2]');
SELECT j, json_set(j, '$[1]', 2), json_valid(j) FROM t;
-- [0x1F]|[31,2]|0
-- [31,2]|[31,2]|0      expected [31,2]|[31,2]|1; SELECT json_valid(j) FROM t gives 1 for this row
```

It happens with json_set(), json_insert(), json_replace(), json_array_insert() and json_remove() when given at least one path (even a NULL one: `json_set('[0x1F]', NULL, NULL)`), and with json_patch() when its first argument is JSON5. The output must be at least 100 bytes long or contain a number that was written in hex. json_valid() with flags 5 or 9 is wrong too. These give the right answer: json() and the one-argument forms (`json('[0x1F]')`, `json_set('[0x1F]')`), short output without hex (`json_set('{k:1}', '$.v', 2)`), JSON5 only in json_patch()'s second argument, and json_valid() with the 0x02 bit (flags 2, 3, 6). Other functions given the same text in the same statement (json_type, json_error_position, `->`, `->>`, json_each) return the right values.

This is not the case reported in "json_set() can construct invalid JSON from a quoted path containing an invalid escape" (2026-05-18). There the text json_set() returns really is invalid. Here the text is valid, and json_valid() says so in a separate statement.

**Cause, as far as we can tell.** The editing functions render the edited JSONB through `jsonReturnParse()`. When the text does not fit `JsonString`'s 100-byte static buffer, `jsonReturnString()` adds that JsonParse to the statement's JSON cache, under the output text. A hex literal is enough, because `jsonTranslateBlobToText()` renders it with `jsonPrintf(100, ...)`, which moves the text out of the static buffer:

```c
if( pParse && pParse->bJsonIsRCStr==0 && pParse->nBlobAlloc>0 ){
  int rc;
  pParse->zJson = sqlite3RCStrRef(p->zBuf);
  pParse->nJson = p->nUsed;
  pParse->bJsonIsRCStr = 1;
  rc = jsonCacheInsert(ctx, pParse);
```

That JsonParse is the editable copy of the input's parse, and `jsonParseFuncArg()` copies the input's flag into it (`p->hasNonstd = pFromCache->hasNonstd;`). So the cache entry for the canonical output still says it uses JSON5. `jsonValidFunc()` finds that entry by text through `jsonCacheSearch()`, and without the 0x02 bit it returns 1 only if `p->hasNonstd==0`.

Clearing the flag before the insert makes every query above give the expected answer. `json_valid('[0x1F]')` is still 0, and 1 with flags 2:

```diff
--- a/src/json.c
+++ b/src/json.c
@@ -874,6 +874,7 @@
         pParse->zJson = sqlite3RCStrRef(p->zBuf);
         pParse->nJson = p->nUsed;
         pParse->bJsonIsRCStr = 1;
+        pParse->hasNonstd = 0;
         rc = jsonCacheInsert(ctx, pParse);
         if( rc==SQLITE_NOMEM ){
           sqlite3_result_error_nomem(ctx);
```

We have only checked it against these queries, so take it as a pointer to the cause rather than a proposed fix.

**Versions** (official amalgamations or tarballs, default options): 3.42.0 (the first that reads JSON5), 3.43.0 and 3.44.0 give the expected results. 3.45.0 (the first with JSONB), 3.46.0, 3.47.0, 3.48.0, 3.49.0, 3.50.0, 3.51.0, 3.53.4, 3.54.0 and trunk dc388e83b05d give the results above; the third query is right in all of them. 3.38.0 to 3.41.0 reject `[0x1F]` as malformed JSON.

We found it with a property-based test generator for SQLite databases and queries: a query gave different results with its common table expression inlined and MATERIALIZED. In the MATERIALIZED form, two rows holding the same JSON text got different json_valid() results.
